# MCP App Provider Development Bootstrap

Status: proposed

## Summary

Extend `tama-kit bootstrap` so an OAuth authorization-server application can
provision a local, containerized Tama `/mcp/app` integration from the provider
application's repository root.

Tama Kit is the development control plane. It detects the provider application,
plans the local topology, generates both owner-specific environment fragments,
adds the Tama container to the provider's Compose project, preserves generated
keys across reruns, and verifies the integration without depending on a
provider-specific CLI.

The separate Memovee CLI remains the customer-facing production control plane
for production Compose/container deployment, domains, TLS, production secret
custody, activation, rollback, and operational state. It does not need to own
local source-development setup.

This work extends the existing provider-root `tama-kit bootstrap` command. It
does not use `tama-kit dev setup`, which is reserved for native development in
a Tama source checkout.

## Decisions

1. Tama runs in the container generated by `tama-kit bootstrap`.
2. Tama Kit runs from the root of the provider application, such as Memovee.
3. `.tama.env` is the private environment for the Tama container and contains
   the Tama-owned `/mcp/app` values and introspection private key.
4. The provider's private values are written to a separate provider-owned
   environment fragment, such as `.memovee.integration.env`.
5. Private keys never share a file or cross ownership boundaries.
6. The provider is described through a versioned, language-neutral contract.
   Tama Kit consumes semantic roles rather than hard-coding Memovee variable
   names.
7. Tama Kit may detect a provider name and environment prefix, but detection is
   only a first-run suggestion. The accepted identity is persisted and never
   silently changes because a directory or repository was renamed.
8. Interactive setup may confirm a detected identity. Non-interactive and JSON
   setup require a persisted identity or explicit provider name/prefix.
9. Preparation and activation remain separate. Bootstrap defaults to
   `prepared`; exposing `/mcp/app` requires explicit activation authority.
10. Tama and the provider remain the final runtime authorities. Both reject
    incomplete or inconsistent generated configuration independently.

## Terminology

- **Provider**: the application acting as OAuth authorization server for Tama's
  `/mcp/app` resource. Memovee is the first provider, but the contract must also
  support future Phoenix, Rails, Node, or other applications.
- **Provider identity**: a stable lowercase name such as `memovee`.
- **Environment prefix**: the stable uppercase environment namespace derived
  from or explicitly assigned to the provider, such as `MEMOVEE`.
- **Public origin**: the exact issuer or resource origin visible to OAuth
  clients and used in token claims.
- **Transport origin**: the address by which the Tama container reaches a
  host-native provider during local development.
- **Prepared**: trust material is present and verifiable, while user-facing
  authorization and Tama `/mcp/app` exposure remain disabled.
- **Enabled**: the prepared configuration has passed verification and the
  provider and Tama expose the integration.

## Goals

- Keep one developer-facing tool for local provider and Tama provisioning.
- Extend the existing provider-root bootstrap planner, writer, Compose, and
  result-envelope implementations instead of creating another generator.
- Work with provider applications in any language or framework.
- Detect a useful provider identity while making the persisted result stable
  and reviewable.
- Generate stable, asymmetric, owner-specific keypairs.
- Keep all generated private files root-ignored, untracked, owner-only, and
  symlink-safe.
- Make repeated runs idempotent and preserve valid existing keys.
- Keep dry-run and JSON output deterministic, non-interactive, and free of
  private keys, tokens, assertions, and setup credentials.
- Verify both public JWKS directions and authenticated introspection before
  activation.
- Support a host-native provider communicating with containerized Tama without
  confusing Docker routing with the public OAuth issuer.

## Non-goals

- Implementing OAuth, JWT, MCP, consent, Actor, grant, refresh, or revocation
  semantics in Tama Kit.
- Editing arbitrary provider application source code.
- Guessing how an application loads environment files without an explicit
  provider contract.
- Sharing one environment file or keypair between Tama and the provider.
- Passing a client-supplied Actor identifier to Tama `/mcp/app`; Tama continues
  to derive the Actor from the validated access-token `sub`.
- Applying Terraform automatically.
- Turning Memovee CLI into a dependency of local development.
- Using the provider name or directory name as a security boundary.

## Command surface

The intended first-run experience is:

```bash
cd /path/to/provider-app

tama-kit bootstrap \
  --mcp-app \
  --port 4001 \
  --start
```

Additional options:

```text
tama-kit bootstrap [path]
  --mcp-app
  --mcp-app-contract <path>
  --provider-name <name>
  --provider-prefix <prefix>
  --provider-origin <absolute-origin>
  --provider-transport-origin <absolute-origin>
  --allowed-origin <absolute-origin>   # repeatable
  --activate
  ...existing bootstrap options
```

Behavior:

- `--mcp-app` opts into provider integration.
- `--mcp-app-contract` selects a contract when discovery is ambiguous or the
  provider uses a non-conventional location.
- `--provider-name` supplies the stable provider identity.
- `--provider-prefix` overrides the environment namespace without changing the
  human-readable provider name.
- `--provider-origin` is the public OAuth issuer origin and is never inferred
  from an incoming HTTP Host header.
- `--provider-transport-origin` is used only when container routing cannot use
  the public origin directly.
- `--allowed-origin` is explicit and repeatable. It must not be inferred merely
  from the provider or Tama origin because browser/MCP Origin policy belongs to
  the actual client context.
- `--activate` is explicit authority to move a verified prepared integration to
  enabled. Without it, bootstrap leaves both sides prepared.
- `--json` remains non-interactive. Missing required identity or topology input
  is an error rather than a prompt or guess.

The exact option names may be adjusted during implementation, but the
authority and non-interactive behavior must remain the same.

## Provider identity detection

### Precedence

Resolve provider identity in this order:

1. Existing Tama Kit managed manifest.
2. Explicit provider contract.
3. `--provider-name` and `--provider-prefix`.
4. Framework-owned application metadata.
5. Git remote repository name.
6. Project-root directory name as the weakest suggestion.

Framework metadata includes:

- Phoenix: the `:app` value returned by the Mix project definition;
- Rails: the application class/module or an explicit application name;
- Node: the `name` in `package.json`; and
- generic projects: no framework-derived identity.

Tama Kit must not execute provider application code merely to detect a name.
Detection reads bounded, known metadata files using parsers appropriate to
their format. If safe static detection is not possible, it falls through to a
weaker suggestion or requires explicit input.

### Interactive behavior

On an initial interactive run:

```text
Detected provider: memovee
Environment prefix: MEMOVEE
Environment file: .memovee.integration.env

Use these values? [Y/n]
```

The detected values are suggestions until accepted. A negative response asks
for an explicit provider name and optional prefix.

### Non-interactive behavior

For JSON, non-TTY, and automation runs:

- use a complete existing manifest or provider contract;
- otherwise require `--provider-name`;
- derive the prefix deterministically only when no explicit prefix is needed;
- return a structured usage/configuration error when identity remains
  ambiguous; and
- never prompt.

### Normalization

Example normalization:

```text
memovee       -> provider name: memovee     prefix: MEMOVEE
my-service    -> provider name: my-service  prefix: MY_SERVICE
Acme OAuth    -> provider name: acme-oauth  prefix: ACME_OAUTH
```

Rules:

- provider names are lowercase ASCII slugs containing letters, digits, and
  single hyphens;
- environment prefixes contain only `A-Z`, `0-9`, and `_`, begin with a
  letter, and have a conservative maximum length;
- repeated separators are collapsed;
- empty or ambiguous results are rejected;
- reserved or conflicting prefixes are rejected; and
- the resolved environment names are checked for duplicates before any write.

The accepted identity is persisted in `tama/.tama-kit.json`, for example:

```json
{
  "mcpAppProvider": {
    "name": "memovee",
    "environmentPrefix": "MEMOVEE",
    "environmentFile": ".memovee.integration.env"
  }
}
```

Subsequent runs use the persisted values. A change requires an explicit
migration command or flag and must show the old and new public names before
writing. Renaming the project directory or changing the Git remote never
renames environment variables automatically.

## Generated provider-root layout

For Memovee, the resulting layout is:

```text
memovee/
├── .memovee.integration.env      # Memovee-owned private values
├── .tama.env                     # Tama-container private values
├── .tama.postgres.env            # Tama PostgreSQL values
├── .tama.env.example             # safe example only
├── compose.yml
└── tama/
    ├── .tama-kit.json
    ├── compose.yaml
    ├── main.tf
    ├── versions.tf
    └── README.md
```

There is no separate `.tama.mcp-app.integration.env`. The container already
loads `.tama.env`, so that file is the correct Tama deployment boundary.

The provider fragment path comes from the accepted provider identity or an
explicit contract. Tama Kit writes it only when the provider contract also
declares how the provider consumes it. The first implementation does not patch
arbitrary application source to add an environment loader.

Supported loading declarations may include:

- an existing shell/direnv fragment already sourced by the repository;
- an existing dotenv file explicitly reserved for the integration; or
- an existing provider Compose service `env_file` entry that Tama Kit can
  safely and narrowly manage.

If no loading declaration exists, Tama Kit may generate a plan and the private
fragment but must report that provider integration is not runnable until the
application-owned loader is configured. It must not report live readiness.

## Ownership and secret placement

| Concern | File or runtime | Owner |
| --- | --- | --- |
| Tama base/container environment | `.tama.env` | Tama Kit for local development |
| Tama PostgreSQL bootstrap values | `.tama.postgres.env` | Tama Kit |
| Provider integration environment | provider-declared fragment | Tama Kit for local development, provider at runtime |
| Provider access-token private key | provider fragment only | provider deployment |
| Tama introspection private key | `.tama.env` only | Tama deployment |
| Provider public verification keys | provider JWKS | provider runtime |
| Tama public introspection keys | Tama JWKS | Tama runtime |
| OAuth and MCP semantics | provider, Tama, and protocol libraries | applications |
| Production Compose and rollout | production CLI/deployment tooling | Memovee CLI for Memovee |

Tama Kit is the development provisioner, not the runtime policy authority.
Generated configuration is accepted only after the provider and Tama validate
it at startup and the live verification gates pass.

## Provider contract

Each provider commits a bounded, non-secret contract compatible with
`tama-mcp-app-bootstrap-v1`. Memovee's existing contract is the first concrete
implementation. The generic schema must include semantic bindings so Tama Kit
does not infer meaning from Memovee-specific variable names.

Example:

```json
{
  "schema_version": "1",
  "compatibility_identifier": "tama-mcp-app-bootstrap-v1",
  "provider": {
    "name": "memovee",
    "environment_prefix": "MEMOVEE",
    "environment_file": ".memovee.integration.env",
    "environment_loader": "existing-shell-fragment"
  },
  "bindings": {
    "mode": "MEMOVEE_TAMA_MCP_APP_MODE",
    "issuer": "MEMOVEE_OAUTH_ISSUER",
    "resource": "MEMOVEE_TAMA_MCP_APP_RESOURCE",
    "access_token_signing_algorithm": "MEMOVEE_OAUTH_SIGNING_ALGORITHM",
    "access_token_signing_key_id": "MEMOVEE_OAUTH_SIGNING_KEY_ID",
    "access_token_private_signing_key": "MEMOVEE_OAUTH_PRIVATE_SIGNING_KEY",
    "access_token_public_overlap_keys": "MEMOVEE_OAUTH_PUBLIC_SIGNING_KEYS",
    "introspection_client_id": "MEMOVEE_TAMA_INTROSPECTION_CLIENT_ID",
    "introspection_jwks_uri": "MEMOVEE_TAMA_INTROSPECTION_JWKS_URI"
  },
  "endpoints": {
    "authorization_server_metadata": "/.well-known/oauth-authorization-server",
    "jwks": "/.well-known/jwks.json",
    "introspection": "/auth/introspections"
  }
}
```

The provider may use conventional names derived from the persisted prefix or
declare every binding explicitly. Once resolved, Tama Kit persists and reports
the exact bindings. It never reconstructs environment names from a changed
directory name on later runs.

For a conventional prefix, the initial roles derive to:

```text
<PREFIX>_TAMA_MCP_APP_MODE
<PREFIX>_OAUTH_ISSUER
<PREFIX>_TAMA_MCP_APP_RESOURCE
<PREFIX>_OAUTH_SIGNING_ALGORITHM
<PREFIX>_OAUTH_SIGNING_KEY_ID
<PREFIX>_OAUTH_PRIVATE_SIGNING_KEY
<PREFIX>_OAUTH_PUBLIC_SIGNING_KEYS
<PREFIX>_TAMA_INTROSPECTION_CLIENT_ID
<PREFIX>_TAMA_INTROSPECTION_JWKS_URI
```

The Tama side keeps the application-owned `TAMA_MCP_APP_*` runtime contract;
provider prefixing does not change Tama's environment names.

## Key generation and exchange

Tama Kit generates or preserves two independent asymmetric keypairs:

1. Provider access-token signing key:
   - private JWK stored only in the provider fragment;
   - current public key published by the provider JWKS; and
   - provider `kid` and algorithm configured into provider-owned variables.
2. Tama introspection assertion key:
   - private JWK stored only in `.tama.env`;
   - current public key published by Tama JWKS; and
   - client ID, `kid`, and algorithm configured into Tama-owned variables.

The cross-configuration contains only public locations and identities:

- Tama receives the provider issuer, resource, JWKS URI, introspection
  endpoint, accepted access-token algorithms, and allowed origins.
- The provider receives the exact resource, Tama introspection client ID, and
  Tama public JWKS URI.

Valid existing keys are preserved byte-for-byte. Rotation is an explicit later
operation with bounded public overlap keys. A normal bootstrap rerun must never
rotate either keypair.

## Public and transport topology

Containerized Tama introduces two address planes that must not be conflated.

Example public topology:

```text
Provider public issuer:  http://127.0.0.1:4000
Tama public origin:      http://127.0.0.1:4001
Tama protected resource:http://127.0.0.1:4001/mcp/app
```

The Tama container cannot use `127.0.0.1:4000` to reach a provider running on
the host, because loopback inside the container refers to the container. Its
transport route may instead be:

```text
Provider transport origin: http://host.docker.internal:4000
```

Tama Kit should add the portable Compose host-gateway mapping where the
container runtime requires it:

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

The public issuer remains the value used for access-token `iss`, authorization
metadata, client-visible URLs, and policy. The transport origin is used only
for container-to-provider HTTP requests.

The current Tama contract binds the provider JWKS and introspection endpoints
to the authorization-server origin. Before implementing host-native provider
support, choose and test one of these runtime contracts:

Resolved (review-01, 2026-09-02): option 2, the single shared origin. See the
Resolutions (review-01, 2026-09-02) section below.

1. Introduce an explicit local transport-origin override. Tama fetches JWKS and
   introspection over the transport origin while validating tokens and metadata
   against the public issuer.
2. Require a hostname that is intentionally reachable with the same origin
   from both the host and container.
3. Require the provider itself to run on the same Compose network.

The recommended first implementation is an explicit transport-origin override
because it supports host-native Phoenix and Rails development without forcing
the provider into a container. It must be opt-in, emitted only by managed local
bootstrap, excluded from normal production configuration, bounded to explicit
local/container transport hosts, and covered by issuer-confusion tests.

Provider reachability must also be verified. On container runtimes where a
host-native server bound only to loopback cannot be reached through the host
gateway, Tama Kit must stop with an actionable diagnostic rather than silently
request a broader bind address. Changing the provider's bind interface remains
application-owned.

## Lifecycle

The lifecycle remains:

```text
disabled -> prepared -> enabled
```

Bootstrap without `--activate`:

1. inspects both contracts;
2. resolves and persists provider identity;
3. generates or preserves both keypairs;
4. writes both owner-specific environments transactionally;
5. starts services only when `--start` is supplied;
6. places both applications in prepared mode;
7. verifies provider metadata/JWKS, Tama JWKS, and authenticated inactive-token
   introspection; and
8. records a secret-free prepared checkpoint.

Activation requires a current successful verification and explicit authority:

1. enable Tama and restart it;
2. verify `/mcp/app` metadata and route availability;
3. enable the provider and restart it;
4. verify the exact resource is advertised; and
5. record a secret-free enabled checkpoint.

If activation fails, remove provider advertisement and Tama route exposure
before changing or removing trust material.

## Planning and write safety

The MCP App extension participates in the existing inspect-plan-write model.
All affected files are planned before the first mutation and written through
one transaction.

Required protections:

- add root-anchored ignore rules before private-file creation;
- reject provider and Tama private files already tracked or staged;
- reject symlinked files and symlinked ancestors;
- preserve user-owned content and unrelated environment entries;
- reject duplicate environment keys;
- reject unmanaged files at paths Tama Kit would own;
- validate JWK type, algorithm, `kid`, public/private members, and size bounds;
- preserve valid existing secrets;
- roll back every changed file if validation or a later write fails; and
- never include private content in change plans, digests exposed to users,
  terminal errors, or JSON output.

`--dry-run` performs no writes, key generation, process startup, network calls,
or state changes. When a secret would need to be created, the plan reports the
future sensitive file operation without materializing the secret.

## JSON result

The public result extends the existing bootstrap envelope with non-secret MCP
App information:

```json
{
  "ok": true,
  "provider": {
    "name": "memovee",
    "environmentPrefix": "MEMOVEE",
    "environmentFile": ".memovee.integration.env",
    "identitySource": "mix-project"
  },
  "mcpApp": {
    "compatibilityIdentifier": "tama-mcp-app-bootstrap-v1",
    "mode": "prepared",
    "providerOrigin": "http://127.0.0.1:4000",
    "tamaOrigin": "http://127.0.0.1:4001",
    "resource": "http://127.0.0.1:4001/mcp/app",
    "providerReachable": true,
    "tamaReachable": true,
    "verified": true
  }
}
```

The result may expose public endpoint URLs, public key IDs, algorithms,
contract versions, file paths, actions, and verification state. It must never
expose private JWK members, compact tokens/assertions, authorization codes,
setup tokens, database passwords, or complete secret-bearing environment
content.

## Memovee integration

Memovee is the first provider implementation:

- provider name: `memovee`;
- environment prefix: `MEMOVEE`;
- provider fragment: `.memovee.integration.env`;
- provider public origin: `http://127.0.0.1:4000` by current local contract;
- Tama public origin: `http://127.0.0.1:4001`;
- exact resource: `http://127.0.0.1:4001/mcp/app`; and
- compatibility identifier: `tama-mcp-app-bootstrap-v1`.

Memovee already owns its OAuth behavior and loads the optional provider
fragment. The implementation should enrich its committed contract with
provider identity, environment-loading metadata, semantic bindings, and any
required transport information. Tama Kit should not contain a branch such as
`if provider.name === "memovee"` for rendering or verification.

## Future provider applications

A future provider integrates by:

1. implementing the same OAuth authorization-server and authenticated
   introspection behavior;
2. committing a compatible provider contract;
3. declaring its stable provider identity and environment bindings;
4. loading its declared private environment fragment; and
5. passing the generic prepared and enabled acceptance suite.

An Elixir package may help Elixir providers implement the runtime protocol, and
a future Ruby gem may provide the same help to Rails. Those are optional
language adapters. The cross-language integration boundary is the versioned
contract plus Tama Kit's bootstrap implementation, not an Elixir library.

## Memovee CLI boundary

Remove or defer local source-development orchestration from the Memovee CLI
plan. In particular, Memovee CLI should not be required for:

- creating local Tama Compose integration;
- writing `.tama.env`;
- generating local provider or Tama keys;
- configuring local provider/Tama trust;
- starting local Tama; or
- running local prepared-state verification.

Memovee CLI remains responsible for the customer-facing production workflow:

- production Compose/container rendering;
- image selection and upgrades;
- production domains, HTTPS, and proxy topology;
- production secret-manager integration and key custody;
- explicit production preparation, verification, activation, rollback, and
  status; and
- production operational state and diagnostics.

The production CLI may consume the same public compatibility contracts, but it
does not delegate production deployment to Tama Kit.

## Implementation phases

### Phase 1: contract and ownership revision

- Add this provider-root/container model to the coordinated WIP documents.
- Define the generic provider contract schema and semantic roles.
- Enrich Memovee's existing contract without weakening its runtime parser.
- Define the public-versus-transport origin contract with Tama.
- Remove Memovee-specific Tama fragment naming from future plans.

### Phase 2: provider identity

- Add safe static identity detection for Phoenix, Rails, Node, Git, and generic
  roots.
- Add interactive confirmation and explicit non-interactive options.
- Add normalization, reserved-prefix, collision, and ambiguity checks.
- Persist the resolved identity and exact variable bindings in the managed
  manifest.
- Add an explicit identity migration path.

### Phase 3: generic environment planning

- Extend `.tama.env` planning with the Tama `/mcp/app` variables and stable
  introspection keypair.
- Add provider-fragment planning through semantic bindings.
- Extend ignore and tracked-file validation to the provider fragment.
- Preserve valid keys and unrelated content across reruns.
- Add safe example/documentation output without live secrets.

### Phase 4: container topology

- Add managed host-gateway support where needed.
- Implement or adopt the agreed transport-origin runtime contract.
- Diagnose provider binding and container reachability failures.
- Preserve the existing internal Tama port `4000` while allowing the external
  host port, normally `4001`, to be selected.

### Phase 5: lifecycle and verification

- Render prepared mode by default.
- Verify contract compatibility and both runtime parsers.
- Verify provider metadata and JWKS.
- Verify Tama JWKS contains the expected introspection key.
- Perform authenticated inactive-token introspection from Tama to the provider.
- Add explicit activation and safe disable-to-prepared rollback.

### Phase 6: documentation and CLI boundary cleanup

- Update Tama Kit bootstrap help, README, generated README, and agent prompt.
- Update Memovee local-development documentation to use Tama Kit only.
- Update or retire Memovee CLI source-development WIP commands.
- Document how a new provider publishes a compatible contract.

## Implementation plan

This section expands the phases above with file-level work items. All
implementation stays on the existing inspect-plan-write path
(`cli/bootstrap/*`, `cli/commands/bootstrap.mjs`); no new generator is
introduced and `tama-kit dev setup` remains out of scope.

### Phase 1 detail: contract and ownership revision

- `cli/bootstrap/mcp-app-contract.mjs` (new): `loadMcpAppContract(root,
  flagPath)`.
  - Explicit `--mcp-app-contract <path>` wins over discovery.
  - Discovery scans `<root>/priv/contracts/` for JSON documents whose
    `compatibility_identifier` is in a constant allow-list
    (`tama-mcp-app-bootstrap-v1`). Zero matches use the conventional
    fallback below; multiple matches fail with a message requesting the
    flag.
  - Structural validation: `schema_version`, lifecycle mode sets,
    `variables` formats, `exact_path` values, optional `provider` identity
    block, `bindings`, `endpoints`, and `environment_loading`.
- `cli/bootstrap/contracts/mcp-app-bootstrap-v1.json` (new, bundled with
  Tama Kit): the Tama-side runtime contract, copied from the Tama source
  repository. `supported_tama_versions` is checked at plan time so the CLI
  stays offline and testable.
- Contract resolution lives in `resolveBindings(source)` in
  `mcp-app-contract.mjs`:
  - Source is a contract: use declared `bindings`; roles the contract omits
    derive conventionally from `provider.environment_prefix`.
  - Source is conventional (no contract): derive all nine roles from the
    resolved prefix:

    ```text
    <PREFIX>_TAMA_MCP_APP_MODE
    <PREFIX>_OAUTH_ISSUER
    <PREFIX>_TAMA_MCP_APP_RESOURCE
    <PREFIX>_OAUTH_SIGNING_ALGORITHM
    <PREFIX>_OAUTH_SIGNING_KEY_ID
    <PREFIX>_OAUTH_PRIVATE_SIGNING_KEY
    <PREFIX>_OAUTH_PUBLIC_SIGNING_KEYS
    <PREFIX>_TAMA_INTROSPECTION_CLIENT_ID
    <PREFIX>_TAMA_INTROSPECTION_JWKS_URI
    ```

    The fragment path derives as `.<providerName>.integration.env` and the
    loader as the conventional shell fragment.
  - The exact resolved bindings are persisted in the managed manifest on
    first write and reported in the plan and result. A contract committed
    later must match the persisted bindings or planning fails; manifest
    precedence prevents silent renaming under an existing fragment.
- Loader verification: a contract's `environment_loading` declaration is
  authoritative. In conventional mode Tama Kit statically checks that the
  fragment filename is referenced (for example `.envrc`, shell rc, or a
  Compose `env_file` entry). When it cannot confirm loading, the plan sets
  `environmentLoading: "unverified"`, prints a warning, and continues; this
  is never a hard failure.
- Enrich Memovee's committed contract in place with the `provider` identity
  block, `environment_loading`, and explicit `bindings`, without weakening
  its runtime parser. This is a tracked cross-repository change.
- Public versus transport origin: no new environment variable is invented.
  Only when `--provider-transport-origin` differs from the public origin
  does the Tama service environment rewrite `TAMA_MCP_APP_AUTHORIZATION_SERVER`,
  `TAMA_MCP_APP_JWKS_URI`, and `TAMA_MCP_APP_INTROSPECTION_ENDPOINT` to the
  transport origin, preserving the same-origin and exact-path invariants.
  Issuer validation always uses the public origin.

### Phase 2 detail: provider identity

- `cli/bootstrap/provider-identity.mjs` (new):
  `detectProviderIdentity({ manifest, contract, flags, root })` with
  precedence: persisted manifest, contract `provider` block, explicit flags,
  static framework metadata, Git remote, directory name.
- Static readers perform bounded file reads only, never executing provider
  code: Phoenix `:app` from `mix.exs` (regex), Rails module from
  `config/application.rb`, Node `package.json#name`, Git remote repository
  name, directory basename.
- `normalizeProviderName` (lowercase ASCII slug) and
  `normalizeEnvironmentPrefix` (`A-Z0-9_`, letter start, at most 24
  characters), plus reserved-prefix and collision checks against existing
  environment files.
- `cli/bootstrap/manifest.mjs`: persist and read an optional
  `mcpAppProvider` key (`name`, `environmentPrefix`, `environmentFile`,
  `bindings`, `environmentLoading`) beside `agentSkills`. `schemaVersion`
  stays `1`: the planner rejects unknown schema versions, so an optional key
  is safe for old readers (ignored) and new readers (tolerates absence).
- `cli/commands/bootstrap.mjs`: add `--mcp-app`, `--mcp-app-contract`,
  `--provider-name`, `--provider-prefix`, `--provider-origin`,
  `--provider-transport-origin`, repeatable `--allowed-origin`, and
  `--activate`. Interactive confirmation covers origins the user did not
  state explicitly; non-interactive runs fail on ambiguity.
- `cli/types.mjs`: `ProviderIdentity`, `McpAppProviderContract`,
  `McpAppPlan`, and the result-envelope `provider` / `mcpApp` blocks.
- Identity migration path: re-resolution never happens automatically; a
  persisted identity changes only through an explicit, confirmed
  re-bootstrap that rewrites the fragment under the new name.

### Phase 3 detail: generic environment planning

- `cli/bootstrap/mcp-app.mjs` (new): `planMcpApp({ plan, flags, identity,
  providerBindings, tamaContract })` producing:
  - the provider fragment content from the resolved bindings, with values
    derived from identity and origins; the provider access-token private
    JWK appears only in the fragment;
  - the Tama environment from the bundled contract's `required_in`
    (mode-driven), including the stable introspection keypair: private JWK
    only in `.tama.env`, public key array in the example file;
  - the keypair plan (two independent RS256 pairs via the existing
    `generateOAuthPrivateJwk` / `validateOAuthPrivateJwk`; thumbprint
    derived kids keep the spaces distinct); create on first write,
    preserve byte-for-byte on rerun, never rotate;
  - the lifecycle mode: `prepared` by default, `enabled` only with
    `--activate`.
- `cli/bootstrap/environment.mjs`: mode-conditional required-variable
  validation driven by the Tama contract for the app path; the existing flat
  required list stays for the non-app path.
- `.tama.env.example` gains public `TAMA_MCP_APP_*` values only; no live
  secret is ever written to an example or committed file.

### Phase 4 detail: container topology

- `cli/bootstrap/compose.mjs`: add the managed `tama` service to the root
  Compose file with the Phase 3 environment; extend `OWNED_SERVICES` with
  `tama` so foreign ownership conflicts are rejected.
- `extra_hosts: ["host.docker.internal:host-gateway"]` is rendered only
  when the transport origin differs from the public origin.
- Preserve the existing internal Tama port `4000`; the external host port,
  normally `4001`, stays selectable. Provider binding and reachability
  failures produce actionable diagnostics naming the concrete origin.

### Phase 5 detail: lifecycle and verification

- `cli/bootstrap/start.mjs` and the plan gate verification behind running
  services; `--activate` performs: contract compatibility for both runtime
  parsers, provider metadata and JWKS fetch, Tama JWKS contains the expected
  introspection key, and authenticated inactive-token introspection from
  Tama to the provider.
- Any verification failure returns both sides to `prepared` before trust
  material is touched. Dry-run performs no network verification.

## Test matrix

### Identity

- Detect Phoenix `:app` without executing Mix tasks.
- Detect Rails and Node metadata from bounded static files.
- Fall back to Git and directory suggestions.
- Interactive acceptance persists the detected name and prefix.
- JSON/non-TTY mode rejects ambiguous identity without prompting.
- Explicit name and prefix override suggestions.
- Directory and Git remote renames do not change persisted identity.
- Invalid, empty, reserved, duplicate, and colliding prefixes fail closed.

### Filesystem and secrets

- Fresh bootstrap creates each private file with mode `0600`.
- Ignore rules are root-anchored and precede file creation.
- Tracked, staged, symlinked, unmanaged, and duplicate-key files fail closed.
- A second run produces zero changes and preserves both keypairs byte-for-byte.
- A provider-only or Tama-only partial keypair fails closed.
- Dry-run creates no secrets or files.
- JSON and human output contain no private key or token material.
- Transaction failure restores every previously changed file.

### Contracts

- Provider and Tama compatibility identifiers match.
- Supported version ranges include the selected provider and Tama image.
- Every semantic role resolves to one exact environment variable.
- Provider and Tama runtime parsers accept the rendered configuration.
- A contract/runtime drift fixture fails before service startup.

### Networking

- Tama container reaches a host-native provider through the managed transport
  route.
- Public issuer and resource identifiers remain unchanged by Docker routing.
- Token issuer validation uses the public issuer, not the transport origin.
- Missing host-gateway support produces an actionable error.
- An unreachable loopback-only provider produces an actionable error without
  changing its bind address.
- Production configuration cannot accidentally enable the local transport
  override.

### Lifecycle acceptance

- Fresh `disabled -> prepared` publishes both public keys without exposing Tama
  `/mcp/app` or provider authorization/token issuance.
- Prepared authenticated inactive-token introspection returns inactive.
- Explicit `prepared -> enabled` exposes the exact resource.
- Active access token reaches Tama `/mcp/app` and Actor identity comes from the
  validated `sub`.
- Refresh rotation, revocation, Actor deactivation, and recipient resolution
  retain application-owned behavior.
- Failed activation returns both sides to prepared before changing trust
  material.

### Provider portability

- Memovee passes using explicit semantic bindings.
- A Phoenix fixture with a different provider name and prefix passes.
- A Rails fixture with different environment names passes.
- A generic fixture with an explicit contract passes without framework
  detection.
- No implementation path branches on the provider name.

## Acceptance criteria

- A developer can run Tama Kit from a provider repository and obtain a local
  provider plus containerized Tama integration without installing or invoking
  the provider's production CLI.
- The provider identity is conveniently detected, explicitly accepted, and
  stable across later directory or repository renames.
- Tama Kit remains provider-neutral and contains no Memovee-specific rendering
  behavior.
- Provider and Tama private keys remain in separate owner-specific `0600`
  files.
- Tama container routing is distinct from and cannot replace the public OAuth
  issuer or resource identity.
- Bootstrap is idempotent, transactional, secret-safe, and machine-readable.
- Prepared verification succeeds before explicit activation.
- The same generic contract can be implemented by a future Rails provider.
- Memovee CLI is no longer required for local development and remains focused
  on production/customer provisioning.

## Open implementation decisions

   application contract is extended in place or references a small provider
   descriptor.
2. Final transport-origin environment variable and the corresponding Tama
   runtime validation rules.
3. Whether explicit activation is part of `bootstrap --activate` or a focused
   `tama-kit integration activate` command.
4. The exact managed-manifest schema migration from existing bootstrap

5. The minimum provider environment-loading declarations supported in the
   first release.

### Resolutions (working, 2026-09-02)

1. Confirmed: discovery is `--mcp-app-contract` first, then
   `priv/contracts/` by compatibility identifier; the existing application
   contract is extended in place with identity, loader, and binding blocks.
   A missing contract falls back to conventional derivation from the
   persisted prefix; scaffolding the missing contract is tracked in
   `wip/mcp-app-contract-scaffolding.md`.
2. Proposed: no new variable name. The Tama service environment rewrites
   the existing `TAMA_MCP_APP_AUTHORIZATION_SERVER`, `TAMA_MCP_APP_JWKS_URI`,
   and `TAMA_MCP_APP_INTROSPECTION_ENDPOINT` values to the transport origin
   when it differs; Tama's existing same-origin and exact-path validation
   applies unchanged.
3. Proposed: explicit activation stays `bootstrap --activate` for the first
   release; a focused `tama-kit integration activate` can follow without
   rework.
4. Proposed: no schema version bump. The managed manifest keeps
   `schemaVersion: 1` and gains an optional `mcpAppProvider` key, safe for
   old and new readers alike.
5. Confirmed: the contract declares `environment_loading`; conventional
   mode performs a static reference check and reports
   `environmentLoading: "unverified"` instead of failing.

### Resolutions (review-01, 2026-09-02)

1. Supersedes working resolution 2: the single shared origin is required. The
   provider public origin must be reachable from both the host (browser/OAuth
   clients) and the Tama container (JWKS and introspection fetches). There is no
   transport-origin override, no separate transport variable, and no rewriting
   of `TAMA_MCP_APP_AUTHORIZATION_SERVER`, `TAMA_MCP_APP_JWKS_URI`, or
   `TAMA_MCP_APP_INTROSPECTION_ENDPOINT`; Tama's existing same-origin and
   exact-path validation applies unchanged. `--provider-transport-origin` is
   removed from the command surface. Compose emits
   `extra_hosts: ["host.docker.internal:host-gateway"]` only when the accepted
   provider origin's host is `host.docker.internal`. A provider that cannot be
   reached through the shared origin stops preparation with an actionable
   diagnostic; changing the provider's bind interface remains application-owned.
2. Confirms working resolution 3 with the provider-owned boundary:
   `bootstrap --activate` keeps both sides prepared during write and prepared
   verification, then enables and restarts Tama, verifies Tama metadata and the
   `/mcp/app` route, and reports the provider enable plus restart as an
   explicit provider-owned step. Tama Kit never executes provider lifecycle
   commands. The enabled checkpoint is recorded only after both sides are
   verified. Activation failure restores both sides to the live prepared state
   before any trust material changes.

These decisions may change CLI spelling and schema layout, but they must not
change the ownership, lifecycle, portability, or secret-safety boundaries in
this document.
